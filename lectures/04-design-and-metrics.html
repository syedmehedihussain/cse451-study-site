01What is software design?

Exam text (Pressman)

Software design is the process of transforming requirements (the WHAT) into a blueprint (the HOW): the architecture, data structures, interfaces and components from which code is built. It is the first place where quality can be assessed and the place where requirements, business needs and technical constraints meet.

Good design exhibits (Mitch Kapor, "Software Design Manifesto")

1 Firmness

No bugs that inhibit its function.

A payroll system never computes a wrong salary.

2 Commodity

Suitable for the purpose it was intended.

A POS app handles barcode, cash and card flows.

3 Delight

Using the program is a pleasurable experience.

A banking app transfers money in two taps.
Memory aid

F-C-D: "Firm Comfy Delight", like a good bed: it does not break, it fits you, you enjoy it.

Tools: UML class, component and sequence diagrams, C4 model; StarUML, Visual Paradigm, Enterprise Architect, draw.io. Industry: design reviews and Architecture Decision Records (ADRs) before coding.

02Modularity: divide and conquer

Exam text

Modularity is the degree to which a system is separated into distinct, named, addressable parts (modules) that can be developed separately and recombined to satisfy the requirements.

  • Why? A monolithic program (one module) has too many control paths, variables and references to understand.
  • Benefits: lower complexity, parallel team work, reuse, easier testing and maintenance.
  • Principle: split until each module does one understandable job, but not further.
  • Good module: describable in one sentence, hides its internals, talks through a small interface.

Monolithic

One 50,000-LOC module: login, catalog, cart, payment and shipping all tangled together.

Modular

Six cohesive modules with clear interfaces.

AuthCatalogCartPaymentShippingNotify

The trade-off: how many modules?

Slider: module count vs costIllustrative model

Curves use 100/n for development and 5n for integration so the minimum lands near 4 to 5 modules, like the slide. The interface count n(n−1)/2 is exact.

  • Under-modularity: few huge modules → each is costly to build, test and understand.
  • Over-modularity: many tiny modules → interface, integration and communication cost explodes.
  • As modules increase, per-module effort falls but integration effort rises. The optimal region M is where total cost is minimum (about 4 to 5 modules on the slide).
  • Rule of thumb: one module = one responsibility that a developer can fully grasp.
Real life

Large e-commerce and streaming platforms split into hundreds of independently deployable services. Teams that over-split into "nano-services" often re-merge them to cut network and deployment overhead.

03Functional independence: cohesion and coupling

Exam text

Functional independence: each module addresses one sub-function and has a simple interface with the rest of the program. It is judged by two criteria: cohesion (functional strength inside ONE module, aim HIGH) and coupling (interdependence BETWEEN modules, aim LOW).

From poor to good modular design

Poor design

class OrderManager {
  public static double taxRate; // global
  void createOrder(...)   {...}
  void printInvoicePDF()  {...}
  void sendSMS(String ph) {...}
  void saveToMySQL()      {...}
}
// Report class writes taxRate directly
Low cohesion: business logic, printing, messaging and storage in one class. High coupling: other classes change the shared taxRate (common coupling). A change to SMS or DB code risks breaking order logic.

Better design

class OrderService {
  OrderService(OrderRepo r, Notifier n)
  Order createOrder(Cart c)
}
class InvoicePrinter { print(Order o) }
interface Notifier  { send(Message m) }
interface OrderRepo { save(Order o) }
class TaxPolicy { double rateFor(Region r) }
Functional cohesion: every class does one job. Data coupling: only the needed parameters. Notifier and OrderRepo can be swapped (SMS → email, MySQL → Postgres) without touching OrderService.

Tools: Extract Class, Move Method, Encapsulate Field, Dependency Injection (Spring, .NET DI, Dagger); SOLID principles. Metrics: LCOM for cohesion; CBO, fan-in and fan-out for coupling (SonarQube, NDepend, JDepend, Structure101).

04Aspects (cross-cutting concerns) and refactoring

Aspect

A concern that cuts across many modules. Requirement A crosscuts B if B cannot be satisfied without taking A into account (every function must log and check security).

Solution: write the concern once as an aspect and "weave" it into all modules (Aspect-Oriented Programming: AspectJ, Spring AOP, PostSharp).

Refactoring

Changing a system so that its external behaviour stays the same while its internal structure improves (remove duplication, simplify, clarify).

Common moves: Extract Method/Class, Rename, Move Method, Replace Conditional with Polymorphism. Always keep tests green.

Before

double total() {
  double t = 0;
  for (Item i : items)
    t += i.price*i.qty;
  if (t > 1000)
    t = t * 0.95;
  return t;
}

After (Extract Method)

double total() {
  return discount(subtotal());
}
double subtotal() {...}
double discount(double t) {...}
Real life

Logging, security and transactions are handled as aspects in enterprise frameworks. XP teams refactor continuously (the "Boy Scout rule": leave the code cleaner than you found it).

06User interface design: why it matters

UI design creates an effective communication medium between a human and a computer. It identifies interface objects and actions, then turns them into a screen layout that becomes a usable prototype. To the user, the interface IS the system.

Typical design errors

Lack of consistency: Save is Ctrl+S on one screen and F2 on another. Too much memorization: the user must remember product codes. No guidance or help. No context sensitivity: same help text everywhere. Obscure or unfriendly: "Error 0x80004005".

A good UI answers "yes" to

Easy to learn? Time for a new user to finish a task. Easy to use? Task time and error rate of regular users. Easy to understand? The user can predict what each control does.

07Theo Mandel's three golden rules

Exam text

1. Place the user in control. 2. Reduce the user's memory load. 3. Make the interface consistent.

1 Place the user in control

Non-forcing modes: enter and exit easily (Esc closes a dialog). Flexible interaction: keyboard, mouse, touch, voice. Interruptible and undoable: Ctrl+Z, drafts are kept. Customizable: macros and shortcuts for experts. Hide technical internals: never type OS commands. Direct manipulation: drag-and-drop, sliders.

2 Reduce the user's memory load

Recognize, don't recall: recent-files list, visual cues. Meaningful defaults: balance shows 0.00, with a reset option. Intuitive shortcuts: Alt+P prints. Real-world metaphors: printer icon, shopping cart. Progressive disclosure: essentials first, "Advanced" later.

3 Make the interface consistent

Meaningful context: titles and breadcrumbs (Home › Courses › CSE451). Consistent across a family: the MS Office ribbon in Word, Excel, PowerPoint. Keep conventions: Ctrl+S always saves. Same look, same action: identical icons, colours and positions.

Memory aid

Control, Memory, Consistency: "Users Must Click". User in control, Memory load, Consistent.

Practice: which golden rule fixes it?

08UI design process and interface analysis

The UI process is iterative (a spiral): interface analysis and modeling → interface design → construction (prototype) → interface validation, then round again.

Users

Who interacts with the system? Skills, education, age, language, frequency of use.

Tasks

What work do users perform, and in which sequence (workflow)?

Content

What information is presented, and how is it organized and formatted?

Environment

Where is it used? Noise, lighting, mobile device, embedded or kiosk system.

Memory aid

U-T-C-E: "Users Type Code Everywhere".

User analysis: know the user

Trained professionals, technicians or casual users? Education, age and gender range? Expert typists or keyboard-phobic? Primary language? Daily use or occasional? Domain experts? Do they care about the technology? What is the consequence of a mistake (a bank transfer)?

Task analysis and modeling

Answers: what work, which tasks and subtasks, which domain objects, in what sequence? Use cases define basic interaction. Task elaboration refines tasks. Object elaboration finds interface objects. Workflow analysis shows multi-role work as a swimlane diagram.

Analysis of display content

  1. Consistent location: the same data type always in the same place (photo top-right).
  2. Partition large reports: paging, tabs or collapsible sections.
  3. Jump to summary: dashboards for large collections of data.
  4. Scale to the device: responsive layout for smartphones.
  5. Meaningful colour: red = error, green = success (never colour alone).
  6. Clear errors and warnings: say what went wrong and how to fix it ("Invalid course code. Use the format CSE451.").

Typography carries a message too: font, size and weight change how content is read.

Anticipation

Predict the user's next move and offer it.

Communication

Report the status of every activity (progress bar).

Consistency

Same navigation, menus, icons and colours on every page.

Controlled autonomy

Free movement, within the app's navigation conventions.

Efficiency

Optimize the user's work, not the developer's.

Focus

Keep content on the task at hand; cut clutter.

Fitts's law

Time to hit a target depends on its distance and size.

Human interface objects

Reuse proven components (Bootstrap, Material UI).

Latency reduction

Let users keep working while operations finish.

Learnability

Minimal learning time; minimal relearning on return.

Work product integrity

Auto-save forms so an error never loses work.

Readability

Legible size, contrast and language for all users.

Track state

Store state so users can log off and resume later.

Visible navigation

Bring work to the user instead of long scrolling.

White space

Don't fear white space; emphasize content over style.

Layout flow

Organize elements from top-left to bottom-right.

Real life

Auto-save (Google Docs), progress indicators (file uploads) and resumable sessions (online banking) apply these daily.

10Fitts's law: sizing and placing targets

Exam text

The time to acquire a target is a function of the distance to it and its size.

T = a + b · log2(1 + D / W)

  • T: movement time to reach the target (s)
  • D: distance from start to target centre
  • W: target width along the direction of motion
  • a, b: device/user constants from experiments
  • log2(1 + D/W): index of difficulty (ID) in bits
Calculator: compare two buttonsSlide 16 and Exercise 2
Worked example from the slide (a = 0.1 s, b = 0.15 s/bit, D = 300 px)

A (W = 20): ID = log2(1 + 300/20) = log2 16 = 4 bits → T = 0.1 + 0.15×4 = 0.70 s
B (W = 100): ID = log2(1 + 300/100) = log2 4 = 2 bits → T = 0.1 + 0.15×2 = 0.40 s

The larger button B is selected about 43% faster.

Real life

Menus on screen edges (effectively infinite width), large "Buy now" buttons, and context menus at the cursor all exploit Fitts's law. The bKash "Send Money" tile is large and near the thumb for the same reason.

12Product metrics: measure, metric, indicator

1 Measure

A quantitative indication of extent, amount or size of an attribute.

24 defects found in review

2 Metric

The degree to which a system or component possesses an attribute.

2.4 defects per KLOC

3 Indicator

A metric (or combination) that gives insight to adjust the product or process.

Density rising → add code reviews
Exam trap

A measure is a raw count (24 defects). A metric relates it to something (per KLOC). An indicator tells you what to do. Give one example of each.

13Function points

Exam text

The Function Point (FP) metric (Albrecht, 1979) measures the functionality delivered by a system, independent of language, from countable information-domain values and a complexity assessment.

EI: External Inputs

Input transactions that update internal files.

add student

EO: External Outputs

Derived data sent to the user.

printed report, invoice

EQ: External Inquiries

Retrieve information without updating files.

search

ILF: Internal Logical Files

A data group maintained inside the system.

order file

EIF: External Interface Files

A data group owned by another application but referenced.

exchange rates
Exam trap

EO vs EQ: an output has derived data (a calculated report, an invoice). An inquiry just retrieves (search, view status). ILF vs EIF: who maintains the data? Inside the boundary = ILF. Owned by another system = EIF.

Memory aid for the weights

Inputs and inquiries are the same: 3-4-6. Outputs are one more: 4-5-7. ILF: 7-10-15. EIF: 5-7-10.

Exam text: the formula

Count total = Σ (count × weight)
FP = Count total × [0.65 + 0.01 × ΣFi]

Fi (i = 1..14) are value adjustment factors, each rated 0 (no influence) to 5 (essential). The VAF ranges 0.65 to 1.35, which is ±35%.

The 14 factors: backup and recovery; data communications; distributed processing; performance critical; heavily used environment; online data entry; multi-screen input; ILFs updated online; complex inputs/outputs/queries; complex internal processing; reusable code; conversion and installation; multiple installations; ease of change and use. Scale: 0 none, 1 incidental, 2 moderate, 3 average, 4 significant, 5 essential.

14Design, class and code metrics

Whitmire's nine characteristics of OO design

Size

Volume, length and functionality (number of classes and operations).

Complexity

How the classes of a design are interrelated.

Coupling

Physical connections between design elements (associations, messages).

Cohesion

Degree to which operations work together for one well-defined purpose.

Sufficiency

The abstraction has the features the current application requires.

Completeness

Has all features needed in any context; indicates reuse potential.

Primitiveness

Degree to which an operation or class is atomic (not composed of others).

Similarity

How alike two or more classes are in structure, function, behaviour, purpose.

Volatility

Likelihood that a design component will change.

Exam trap

Sufficiency = features the current application needs. Completeness = features needed in any context (reuse).

Model answer (from the course template)

(a) Kapor's three design qualities

QualityDefinition10ms problemFix
FirmnessNo bugs that inhibit its functionStudents cannot track course progress: a core function is brokenReliable progress tracking (last-watched lesson saved to server); no crashes, no data loss on logout

(b) Modularity

The dashboard is monolithic: one module handles user management, content, payments AND reports. It has low cohesion (many unrelated jobs) and high coupling (changing payment logic can break reporting). Understanding it needs all four domains at once, which makes it intellectually unmanageable.

Redesign: four modules: User Management, Content, Payment, Report. Each has one responsibility (high cohesion) and they talk through defined interfaces (low coupling).

Trade-off: too few modules = low integration cost but high complexity; adding "batch enrollment" touches the whole monolith. Too many = each is simple, but integration cost rises: 20 modules give 20 × 19 / 2 = 190 possible interfaces. The optimum minimizes development + integration cost; four domain-aligned modules is a reasonable balance.
