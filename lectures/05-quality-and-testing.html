01What are software quality attributes?

Exam text

Quality attributes (quality factors) are the non-functional characteristics that describe how well a system delivers its functions: how easy it is to use, how fast it runs, how often it fails and how it handles unexpected conditions.

Functional requirement: WHAT the system doesQuality (non-functional) requirement: HOW WELL it does it
"The system shall let a student pay for an order from the campus wallet.""Payment shall complete in ≤ 2 s for 95% of requests at 300 concurrent users."

Only the right one is testable: it has a pass/fail number.

Rarely stated explicitly

Customers say "user-friendly, fast, reliable". The analyst must turn these into numbers.

They drive architecture

Caching, replication, encryption and modularity are chosen because of quality goals.

Retrofitting is expensive

Re-architecting a finished system for quality costs far more than designing for it up front.

Industry practice

Google and Amazon express them as SLOs. ISO/IEC 25010 standardises the vocabulary.

02Two lenses: McCall's triangle and ISO/IEC 25010:2023

Memory aid

Revision = MFT ("Make Fixes Twice"). Transition = PRI ("Portable, Reusable, Interoperable"). Operation = CREIU ("Can Rabbits Eat Ice Underground?").

ISO/IEC 25010:2023 product quality model

Functional suitability

Complete, correct, appropriate.

Performance efficiency

Time, resources, capacity.

Compatibility

Co-existence, interoperability.

Interaction capability

Formerly "usability"; includes inclusivity.

Reliability

Faultlessness, availability, recoverability.

Security

Confidentiality, integrity, authenticity.

Maintainability

Modularity, analysability, testability.

Flexibility

Formerly "portability"; includes scalability.

Safety new in 2023

Fail-safe, hazard warning.

It replaces ISO 9126. Use it as a checklist during elicitation so no attribute is forgotten.

Exam trap

In the 2023 version "usability" is renamed interaction capability, "portability" is renamed flexibility, and safety is new. McCall's model is from 1977 and has 11 factors in three groups.

Exam trap

Availability is about being up (% of time). Reliability is about not failing while running (probability, MTBF). A system can be available 99.9% and still give wrong answers.

04Availability math, "the nines" and error budgets

Exam text

A = MTTF / (MTTF + MTTR)
Downtime = (1 − A) × 8,760 h per year

MTTF: mean time to failure. MTTR: mean time to repair. Each extra "9" costs roughly 10× more engineering.

AvailabilityDowntime per year
99%3.65 days
99.9%8.76 hours
99.95%4.38 hours
99.99%52.6 minutes
99.999%5.26 minutes

SLI

The indicator you measure, e.g. % of successful requests.

SLO

The internal target, e.g. 99.9% success over 30 days.

SLA

The contract with the customer, with penalties.

Error budget

1 − SLO = 0.1% of 30 days = 43.2 min. Budget spent → freeze features, fix reliability.

Worked example and insight

MTTF = 500 h, MTTR = 2 h → A = 500 / 502 = 0.9960 → 99.60%. Cutting MTTR (fast alerts, auto-restart, one-click rollback) is often cheaper than raising MTTF.

Key link

Maintainability depends on how easily code can be understood, changed and tested, so it is tightly coupled to flexibility and testability. High maintainability is critical for products that are revised often or built fast.

Which attributes matter, to whom, and where?

Primary audience

Users: availability, efficiency, integrity, interoperability, reliability, robustness, usability. Developers: flexibility, maintainability, portability, reusability, testability.

By system type

Embedded (pacemaker, ABS, elevator): efficiency, reliability, safety, installability, serviceability. Internet and mainframe (bKash, Daraz, core banking): availability, integrity, maintainability, scalability. Desktop (MS Office, IDEs): interoperability, usability. AI/ML (chatbots, credit scoring): fairness, explainability, robustness to adversarial input, privacy.

Different parts of one product need different mixes: efficiency for the payment engine, usability for the checkout screen.

Not symmetric

More integrity (authentication, encryption, virus scans) slows the system, but more efficiency does not weaken integrity.

Exercise A: availability, measurable NFRs and trade-offs

The UniCafe order server has MTTF = 720 h and MTTR = 4 h. The SLA demands 99.5%. (a) Compute availability; is the SLA met? (b) Expected downtime in a 30-day (720 h) month? (c) Maximum MTTR that satisfies the SLA? (d) Rewrite "The app should be reliable and fast" as two measurable requirements. (e) The team adds MFA and end-to-end encryption. Which attributes may suffer?

Full solution

(a) A = 720 / (720 + 4) = 0.99448 → 99.45% ✗ misses 99.5%.

(b) Downtime = (1 − 0.99448) × 720 h ≈ 3.98 h ≈ 4 h per month.

(c) 720 / (720 + MTTR) ≥ 0.995 ⇒ MTTR ≤ 720 × 0.005 / 0.995 = 3.62 h (about 3 h 37 min). Target: automated failover/rollback.

(d) RE-1: ≥ 99.5% of payment transactions complete without error each month. PE-1: p95 order placement ≤ 800 ms at 300 concurrent users.

(e) Integrity ↑ but efficiency/performance ↓ (extra crypto and checks), usability ↓ (extra login step), interoperability ↓ (harder integration).

08What is software testing, and who should do it?

Exam text

Testing is the process of exercising a program with the specific intent of finding errors before delivery to the end user. Testability is simply how easily a program can be tested.

"Program testing can be used to show the presence of bugs, but never to show their absence." (E. W. Dijkstra)

A test run reveals errors, performance, requirements conformance, and an indication of quality.

DeveloperIndependent tester
Understands the systemMust learn the system
Tests "gently", driven by deliveryTries to break it, driven by quality
Owns unit and integration tests, TDDExploratory, system and acceptance tests

Modern agile teams use "whole-team quality": SDETs embedded in squads; developers automate, testers explore and assess risk. Remember Lecture 1: a defect found in maintenance can cost 100× one found in requirements.

V&V and the V-model

VerificationValidation
"Are we building the product right?" Tasks that ensure the software correctly implements a specific function."Are we building the right product?" Tasks that ensure the built software is traceable to customer requirements.
Reviews, inspections, static analysis, unit testsAcceptance tests, beta tests, usability studies

The V-model pairs requirements ↔ acceptance, system design ↔ system testing, architecture ↔ integration, module design ↔ unit testing (Lecture 2). Test cases for each level are designed during the matching design phase (early test design = shift-left). The V&V wording is from B. Boehm.

09Testing strategy: in the small, then in the large

Exam trap

The anti-pattern is the "ice-cream cone": mostly manual and E2E tests, few unit tests → slow, flaky feedback. A variant, the Testing Trophy (Kent C. Dodds), stresses integration tests for web front-ends.

Eight strategic issues (Pressman)

  1. Specify requirements quantifiably long before testing starts.
  2. State test objectives explicitly (coverage, MTBF, defect density).
  3. Profile every user category (personas, use cases).
  4. Plan "rapid-cycle" testing with fast feedback.
  5. Build robust software that tests itself (assertions, self-diagnostics).
  6. Use technical reviews as a filter before testing.
  7. Review the test strategy and test cases themselves.
  8. Continuously improve the test process with metrics.

Continuous testing: shift left and shift right

Plan→Code→Build→Test→Release→Operate

Shift-left

Requirement and design reviews. Static analysis in the IDE. TDD / unit tests on every commit. Contract tests before integration.

SonarLint, Semgrep, pytest, Pact

Shift-right

Canary releases and feature flags. A/B tests with real users. Synthetic monitoring. Chaos engineering in production.

LaunchDarkly, OpenTelemetry, Gremlin

10Level 1: unit testing

Exam text

Tests the smallest testable unit (function, method, class) in isolation, usually by the programmer who wrote it, before integration.

  • Driver: a "main program" that feeds test data to the unit and prints results.
  • Stub: stands in for lower-level modules not yet built; returns canned values.
  • Test doubles today: dummy, stub, mock, spy, fake (Mockito, unittest.mock, Jest mocks).
  • What to test: interface, local data structures, boundary conditions, independent paths, error-handling paths.
# test_grade.py
import pytest
from grade import letter_grade

@pytest.mark.parametrize("score, expected", [
    (95, "A"), (80, "B"), (65, "C"), (40, "F")])
def test_letter_grade(score, expected):
    assert letter_grade(score) == expected

def test_rejects_invalid_score():
    with pytest.raises(ValueError):
        letter_grade(105)

$ pytest -q   →  5 passed in 0.03s
Exam trap: driver vs stub

The driver is above the unit and calls it. The stub is below the unit and is called by it. Top-down integration needs stubs; bottom-up needs drivers.

Exam text

Integration testing assembles the software step by step while running tests to uncover errors in the interfaces between modules.

Regression and smoke testing

Regression testing

Re-executing a subset of tests already run, to ensure changes have not propagated unintended side effects.

Any change (code, docs, data) can break existing behaviour. Suite = representative sample + tests for affected functions + tests for changed components. Modern: test-impact analysis, flaky-test quarantine, visual regression.

Smoke testing

A quick, broad check of each daily build to expose "show-stopper" errors before deeper testing starts.

Code is integrated into a daily build; tests target errors that would keep the build from working; benefits: lower integration risk, easier diagnosis, visible progress.
Commit / PR→Build→Smoke (about 5 min)→Regression (about 30 min)→Deploy to stagingfail → block merge, notify author

12Object-oriented and higher-order testing

  • Class testing = OO unit testing. Test the operations of the class and its state behaviour.
  • An operation cannot be tested alone: its result depends on the object's state.
  • Inherited operations must be retested in every subclass context.

Thread-based

Integrate the classes needed to respond to one input or event.

Use-based

Integrate the classes needed for one use case: independent classes first, then dependent layers.

Cluster testing

Integrate the classes needed to demonstrate one collaboration (from CRC or collaboration diagrams).

14Black-box: partitions, boundaries, decision tables

Spec: a student may register for 9 to 15 credits per semester.

  • Equivalence partitioning: split inputs into classes that behave the same; one test per class (e.g. 5, 12, 20, "abc").
  • Boundary value analysis: errors cluster at edges. Test min−1, min, min+1, max−1, max, max+1.
  • Pairwise: 3 browsers × 3 OS × 2 languages = 18 combinations; only 9 tests cover every pair (tool: PICT).
  • State transition: test every valid transition and at least one invalid one.

15White-box: basis path testing and cyclomatic complexity

Node: one or more procedural statements (a sequence can collapse into one node). Edge: flow of control between nodes. Region: area bounded by edges and nodes (the outside counts as one). Predicate node: contains a condition; two or more edges leave it.

Path 1: 1-11
Path 2: 1-2-3-4-5-10-1-11
Path 3: 1-2-3-6-8-9-10-1-11
Path 4: 1-2-3-6-7-9-10-1-11

1-2-3-4-5-10-1-2-3-6-8-9-10-1-11 is NOT independent: it only combines paths 2 and 3, with no new edge.

1 Draw flow graph2 Compute V(G)3 Find basis set4 Write test cases
Exam text: cyclomatic complexity

A quantitative measure of a program's logical complexity = the number of independent paths in the basis set = the upper bound on tests needed for basis-path coverage.

V(G) = number of regions = E − N + 2 = P + 1

Here: 4 regions; 11 − 9 + 2 = 4; 3 predicate nodes + 1 = 4.

Uses: sets the number of basis-path test cases; a testability requirement (TE-1: V(G) ≤ 20 per module; many teams use ≤ 10); a refactoring trigger in code review. Compound conditions: if (a && b) counts as 2 predicates. Modern twist: SonarSource "cognitive complexity" also penalises nesting.

16Measuring test adequacy: coverage and mutation

Coverage criteria, weak to strong

Statement: every line runs once<Branch: every decision T and F<Condition: every sub-condition T/F<MC/DC: each condition shown to matter (DO-178C avionics)<Path: every path (often infeasible)
Exam text: formulas

Statement coverage = executed statements ÷ total × 100%
Mutation score = killed ÷ (total − equivalent) × 100

Mutation testing tests your tests: a tool injects small faults ("mutants": > → >=, + → −, delete a statement). Run the suite: a mutant is killed if any test fails, survived otherwise. Survivors reveal weak assertions or missing boundary tests.

Example

50 mutants, 4 equivalent, 40 killed → 40 ÷ 46 = 87%. The 6 survivors each become a new test.

Exam trap

100% coverage ≠ bug-free. Coverage shows what ran, not what was checked. Do not forget to subtract equivalent mutants in the denominator.

Tools: JaCoCo, coverage.py, Istanbul/nyc, Codecov; PIT, Stryker, mutmut.

17Debugging, cutting-edge techniques and the toolchain

Test execution→Symptom (unexpected result)→Suspected causes→Additional tests→Identified cause→Correction + regression tests↻ iterate until the cause is isolated

Why debugging is hard

Symptom and cause may be far apart. The symptom may vanish when another bug is fixed. The cause may be a combination of non-errors (round-off), a system or compiler error, timing, or an assumption everyone believes.

Classic techniques

Brute force: memory dumps, traces, print statements. Most common, least efficient. Backtracking: trace source backward from the symptom; works for small programs. Cause elimination: form a hypothesis, design data to prove or disprove it; binary partitioning.

Modern toolbox: git bisect (binary search over commits = automated cause elimination); IDE debuggers; observability (OpenTelemetry, Sentry); record and replay (rr); AI assistants (explain stack traces, suggest fixes; verify).

Cutting-edge techniques

TDD and BDD

Red → Green → Refactor. BDD writes executable specs in Given-When-Then (Gherkin).

Cucumber, behave, Reqnroll

Property-based testing

State an invariant (reverse(reverse(xs)) == xs); the tool generates hundreds of inputs and shrinks failures.

Hypothesis, QuickCheck, fast-check

Contract testing

Consumers publish expectations; providers verify them in CI, so microservices deploy independently.

Pact, Spring Cloud Contract

Fuzzing

Random or mutated inputs, guided by coverage, find crashes and security holes.

AFL++, libFuzzer, OSS-Fuzz

Visual and a11y regression

Screenshot diffing catches layout breaks; automated WCAG checks catch accessibility regressions.

Percy, Applitools, axe-core

AI-assisted testing

LLMs draft unit tests and data; self-healing UI locators; risk-based test selection. Always review assertions.
