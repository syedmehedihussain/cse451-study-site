01What is software?

Most people think software is only code. The lecture uses Pressman's wider definition. Software has three parts, and all three are part of the product.

Exam text: definition (Pressman)

Software is the set of computer programs, the data structures they manipulate, and the documentation that describes their operation and use. It is a product, and also the vehicle that delivers information and controls other products.

Programs

Executable instructions that deliver features, function and performance.

Mobile banking app: Android and iOS app code, server APIs, payment engine.

Data

Data structures and stored information that the programs work on.

Mobile banking app: accounts, transactions, configuration files.

Documentation

Descriptive material for users, developers and operators.

Mobile banking app: SRS, API specification, user guide, deployment manual.

Two product types

TypeWho it is forExample from the slideLocal example
Generic productSold on the open market to anyoneMS Office, PhotoshopTally accounting software sold to many shops
Customised productBuilt for one client and its needsA hospital's patient-management systemThe NID system built only for the Election Commission
Real life

When bKash ships a new app version, the "software" is not only the APK. It is also the customer database it reads and the API document that the merchant partners use. If the API document is wrong, the product is broken for the merchants even if the code is perfect.

02Why do software systems fail?

The lecture gives five reasons. Learn each reason with its result, because exam case studies ask you to name the reason behind a failure.

Requirements mismatch

The system does not meet the business need.

Result: it is abandoned, or it needs costly adaptive maintenance.

Performance shortfall

It is too slow or it cannot scale for real users.

Result: rework at extra cost.

Latent errors

Hidden defects surface only in operation.

Result: patches, outages, lost trust.

User rejection

Users were not involved, or not committed.

Result: the system is not used.

Unmaintainability

Accepted at first, then too costly to change.

Result: it falls into disuse.

Lessons from industry

CaseYearFailure typeWhat happened
Ariane 51996Latent errorReused code overflowed a number conversion. The rocket self-destructed about 40 s after launch.
Therac-251985-87Latent errorRace conditions in the control software caused radiation overdoses.
Healthcare.gov2013PerformanceThe site collapsed under launch-day load. Very few users could enrol.
Knight Capital2012Change / deploymentA faulty deployment lost about US$440 M in 45 minutes.
Practice: name the failure reason

An admission-result website for a public university goes down every year on result day because 2 lakh students open it at the same time.

A ministry buys an e-file system. Office staff were never asked about their work, so they keep using paper files and the system stays unused.

A ride-sharing app charges double fare only when a trip crosses midnight. The bug was in the code from the first release.

A garments factory's new payroll system cannot handle overtime rules, which are the main part of its payroll.

A bank's 15-year-old system has no documentation. Every small change takes months, so the bank stops changing it and starts a replacement.

Rule of thumb: did it fail on day one with real users (performance or rejection), later because of a hidden bug (latent), because it does the wrong job (mismatch), or because nobody can change it (unmaintainable)?

03The software crisis

Exam text: software crisis

The persistent failure to deliver software on time, within budget and at the required quality, as system complexity outgrows development practice. The term became widely used at the 1968 NATO Software Engineering Conference.

Three symptoms

Delays

Deadlines slip. Features arrive late or never.

Over budget

Estimates are optimistic. Cost overruns are common.

Low quality

Delivered with many faults. Hard to maintain.

Five root causes

Growing complexityChanging requirementsPoor estimationWeak process and testingPoor communication
Memory aid

C-R-E-P-C: "Complex Requests Every Project Collapses". Complexity, Requirements change, Estimation, Process and testing, Communication.

Key point

The aim of SE is to solve the crisis: fault-free software, on time, within budget, that meets users' needs. The crisis is still with us more than 55 years later. Only the scale changed (cloud, mobile, AI).

Real life: the midterm case

The Bangladesh NID system crashed often, mapped data wrongly, and went 40% over budget. That is all three symptoms at once: low quality (crashes, wrong mapping), over budget (40%), and in practice delays. The exam asked you to connect this to the crisis. See the model answer in section 19.

04What is software engineering?

Exam text: IEEE definition

Software engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software.

Each word in the definition has a meaning. Examiners like you to explain the three key words.

Systematic

Follows a defined process, not ad-hoc coding.

Disciplined

Uses standards, reviews and configuration control.

Quantifiable

Effort, cost, size and defects are measured.

Goal

Fault-free software, on time, within budget, that satisfies users.

It covers the whole life of the product: design, development, testing, deployment and maintenance.

SE as a layered technology (Pressman)

Memory aid

Bottom to top: Q-P-M-T, "Quality People Make Things". Quality focus, Process, Methods, Tools.

Exam trap

The base layer is "a quality focus", not "process". Students often draw process at the bottom. Process is the second layer: it is the glue that holds the technology layers together.

A bridge is the product. Civil engineering is the discipline that makes it safe, on budget and maintainable. Software is the bridge. Software engineering is the civil engineering.

The CS view investigates many ways to produce software, good and bad (for example, a faster shortest-path algorithm). The SE view keeps only techniques that make sound economic sense (for example, building, testing, deploying and maintaining a ride-sharing app such as Pathao that uses that algorithm).

Exam trap: "SE vs just writing programs"

The midterm asked how SE differs from simply writing programs. Do not answer "SE is bigger". Give the table points: product vs process, one person vs team, "it works" vs quality and maintainability, and add that SE covers the whole life cycle including maintenance, which is 60 to 80% of the cost.

06What makes software different?

Software is not like a physical product. These eight characteristics explain why it needs its own engineering discipline.

Logical, not physical

Intangible. You cannot see or touch it, so progress is hard to observe.

Developed, not manufactured

The cost is in the engineering. Copying is almost free.

Deteriorates, does not wear out

Changes add side-effect defects, and it ages against new platforms.

Mostly custom-built

Built to requirements, though reuse of libraries and APIs keeps growing.

A differentiator

Products compete on their software.

A supermarket cashier workstation.

No spare parts

A failure is a design or code error. There is no worn part to swap.

Complex and changeable

Many interacting parts, and it is always expected to change.

Example

A phone's battery wears out. Its OS "ages" as new apps and APIs expose incompatibilities.

Exam trap

"Software wears out" is wrong. Hardware wears out (physical fatigue). Software deteriorates because of change. You will see this again in the failure curves (sections 15 and 16).

10Types of software maintenance

Maintenance is not only bug fixing. Four types share all maintenance effort, and bug fixing is the small part.

effort
share
  • Corrective about 20%
  • Perfective about 48%
  • Adaptive about 16%
  • Preventive about 16%

Corrective 20%

Fixes a reported fault.

The app crashes when the cart is empty.

Perfective 48%

Improves features, usability or performance.

Add dark mode; make checkout faster.

Adaptive 16%

Keeps up with a changing environment.

Support a new OS version or payment API.

Preventive 16%

Avoids future faults and improves maintainability.

Refactor duplicated code; upgrade old libraries.
Where the numbers come from

Enhancement is about 80% of maintenance. Inside that 80%: perfective is 60%, adaptive is 20%, preventive is 20%.

perfective = 0.60 × 80 = 48%   adaptive = 0.20 × 80 = 16%   preventive = 0.20 × 80 = 16%   corrective = 100 - 80 = 20%

Tools: Jira (change tickets), Git (versions and branches), Dependabot (adaptive and preventive library updates), SonarQube (refactoring targets).

Classifier: SmartCanteen change requests and more

CR1: The app crashes when the cart is empty.

CR2: bKash releases a new payment API; the old one will be retired.

CR3: Students ask for dark mode and one-tap re-order.

CR4: The team refactors duplicated checkout code and upgrades a library nearing end-of-support.

CR5: Receipts show the wrong VAT amount.

CR6: A new government e-invoice rule requires a new receipt format.

Extra: Update the app so it runs on Android 15.

Extra: Make menu search return results in 1 s instead of 3 s.

Rule of thumb: broken now = corrective. World changed = adaptive. Users want it better = perfective. Nothing wrong yet, but we protect the future = preventive.
Exam trap

"Wrong VAT amount after a new VAT law" is adaptive (the law changed). "Wrong VAT amount with the same old law" is corrective (the code is wrong). Read whether the environment changed.

Memory aid

1, 5, 10, 20, 150. Each step roughly doubles after design, then release multiplies it by about 7.

Why the curve explodes

  • The earlier a defect is found, the cheaper and easier it is to fix.
  • A late fault forces rework of every artefact built on it: spec, design, code, tests, docs.
  • In production you add outages, data repair, re-release and lost customers. This is often 100× or more of the requirements-phase cost.

Coding is the small part

Only about 20% of development effort. Thinking and checking dominate.

Maintenance is the largest cost

Quality pays back

Good design and testing now reduce maintenance effort later.

14Cost of change: before vs after release

Before release

A change edits documents and models, which is cheap. Validate requirements with prototypes and reviews while change is still easy.

After release

A change touches code, data, tests, docs and live users. Every change risks side effects and regression.

Flattening the curve

Short iterations, automated regression tests and CI/CD make later change cheaper, but never free.

15Hardware: the bathtub curve

1 Infant mortality

High but falling failure rate from design or manufacturing defects and poor components.

A new device failing in its first days.

2 Useful life

Low, stable rate with only random failures.

A TV working reliably for years.

3 Wear-out

Rate rises with wear, fatigue, corrosion and environment.

An old car engine needing frequent repair.

16Software: idealized vs actual failure curve

Idealized curve

Bugs are found and fixed. The failure rate falls and stays low. It assumes no new defects and no changes.

Actual curve

Every change adds new bugs. The rate spikes, falls after debugging, and complexity keeps growing.

Industry controls

Regression testing, CI, code review, canary releases, crash analytics (Firebase Crashlytics, Sentry).

17Software myths

Myths are beliefs that sound right but cost time and money. The lecture groups them by who holds them. Tap each myth to see the reality.

Management myths

"We have a book of standards. That's all my people need."

Is it used, complete and up to date with modern practice? Usually not. Standards help only when they are followed and adapted.

"We bought the newest computers, so we have state-of-the-art tools."

Hardware is not process. Productivity comes from good methods, tools and trained people.

"Behind schedule? Add more programmers and catch up."

Brooks's Law: adding people to a late project makes it later. Onboarding and communication overhead grow as n(n−1)/2. Try the slider below.

"We outsourced it, so we can relax."

If you cannot manage a project in-house, you will struggle to manage it outsourced. You still need clear specs and oversight.

Customer myths

Vague requirements: "A general statement of objectives is enough to start coding; details later."

Poor up-front definition is a major cause of failed projects. Ambiguous requirements mean building the wrong system.

Cost-free change: "Software is flexible, so changes are easy and cheap at any time."

Change is never free. The later it comes in the SDLC, the more it costs (see the cost-of-change curve).

Off-the-shelf magic: "Just buy a package or use open-source modules. Little effort."

Integrating and customising third-party parts for unique business rules can cost as much as building, and adds hidden dependencies.

Practitioner myths

"Once the program runs, our job is done."

Most effort, often 60 to 80%, comes after first delivery, in maintenance.

"I can't assess quality until the program is running."

QA starts on day one. Technical reviews and design checks catch logic and design faults more effectively than testing finished code.

"Working code is the only deliverable; documentation slows us down."

Code is one part of the configuration. Without architecture diagrams, API specs, deployment guides and data dictionaries, software is unmaintainable.

18Worked exercises from the slides

Exercise 1: The cost of bugs in "SmartCanteen"

SmartCanteen is a food-ordering app for a university canteen. Fixing one fault found in requirements costs BDT 1,000. Faults found: requirements 10 (1×), design 15 (5×), coding 20 (10×), testing 8 (20×), maintenance 5 (150×).

  1. (a) Total cost of fixing all faults.
  2. (b) Cost if every fault had been caught in requirements. How many times cheaper?
  3. (c) What % of faults, and what % of cost, come from post-release faults?
  4. (d) Suggest two practices to cut this cost.

Hint: cost = faults × BDT 1,000 × multiplier.

Full solution
PhaseCalculationCost (BDT)
Requirements10 × 1,000 × 110,000
Design15 × 1,000 × 575,000
Coding20 × 1,000 × 10200,000
Testing8 × 1,000 × 20160,000
Maintenance5 × 1,000 × 150750,000
Total58 faults1,195,000

(a) Total = 10,000 + 75,000 + 200,000 + 160,000 + 750,000 = BDT 1,195,000.

(b) All in requirements: 58 × 1,000 = BDT 58,000. 1,195,000 ÷ 58,000 ≈ 20.6× cheaper.

(c) Post-release: 5 ÷ 58 = 8.6% of faults, but 750,000 ÷ 1,195,000 = 62.8% of cost.

(d) Shift left: requirement and design inspections, prototyping with users, test-driven development, CI with automated regression tests.

Insight

Fewer than 1 in 10 faults caused almost two-thirds of the cost.

10 marks

Practice case: "Pathao Food" maintenance and myths

After launch, Pathao Food received these requests: (1) the app shows a blank screen on Android 8; (2) Google Maps changes its pricing and API, so the team must move to a new map SDK; (3) restaurants want a sales dashboard; (4) the team splits a 3,000-line OrderService into smaller classes. The product head says: "We are late for Eid. Hire 6 more developers for the team of 5." (a) Classify the requests and justify. [4] (b) Name the myth, compute communication paths, and give the reality. [3] (c) Draw and explain why the app's failure rate will rise over time even though "software does not wear out". [3]

Model answer

(a) (1) Corrective: a fault in current behaviour. (2) Adaptive: the external environment (map API) changed. (3) Perfective: a new feature users asked for. (4) Preventive: nothing is broken yet; it improves maintainability and avoids future faults.

(b) Management myth: "add more programmers to catch up". Brooks's Law says adding people to a late project makes it later. Paths: 5·4/2 = 10 before; 11·10/2 = 55 after, 5.5× more. New people also need onboarding from the existing team. Better: cut lower-priority scope for the Eid release.

(c) Sketch the actual software curve: a falling idealized line, and an actual line with a spike at each change. Each update adds side-effect defects, the rate falls after debugging, but the minimum creeps up. So software deteriorates because of change, not physical wear. Controls: regression testing, CI, code review, canary releases, crash analytics.

How marks are lost
  • Giving a definition but not linking it to the scenario's problems.
  • Writing "add testing" without saying which testing and why (cost multiplier, latent errors).
  • Forgetting the numbers: 1/5/10/20/150, 60 to 70%, 60 to 80%, n(n−1)/2.
