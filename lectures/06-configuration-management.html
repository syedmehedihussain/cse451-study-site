Software configuration management

Controlling change across the software life cycle: identification, version control, change control, auditing and reporting. Then the whole chapter applied to one regulated project, MediTrack.

01What is software configuration management?

Exam text: definition

SCM is a set of umbrella activities, applied throughout the software process (not at the end), that identify change, control change, ensure change is properly implemented, and report change to everyone who has a stake in it. SCM protects the project from uncontrolled change without blocking justifiable change.

Exam text: First Law of System Engineering (Bersoff)

Wherever you are in the life cycle the system will change, and the desire to change it never goes away.

SCM assumes change, and engineers for it.

The five SCM tasks

1 Identification

Name, classify and track every artefact as an SCI.

2 Version control

Manage versions and variants and their dependencies.

3 Change control

Evaluate, approve, implement and verify each change.

4 Configuration audit

Confirm the change was made correctly and completely.

5 Status reporting

Who changed what, when, and what it affects.

Memory aid

I-V-C-A-S: "I Very Carefully Audit Software".

Four sources of change

New business or market conditions

Revised requirements, new rules.

Business reorganisation or growth

Changed priorities and team structure.

New stakeholder needs

Added functions, new data, new services.

Budget or schedule constraints

Re-scoping of the system.

Real life

The Linux kernel absorbs about 75,000 commits a year from about 4,000 developers. Every one is an SCM transaction with a traceable author, reviewer and release. SCM underpins every regulated release: IEC 62304 medical software, DO-178C avionics, ISO 26262 automotive.

02Software configuration items (SCIs)

Exam text

A Software Configuration Item is any named, uniquely identified unit of information created during the software process that is placed under configuration control.

The complete set of SCIs for a product is its software configuration. SCIs may be basic objects (one document, one source file) or aggregate objects (a design model made of many diagrams).

Requirements

SRS, use cases, user stories, acceptance criteria, traceability matrix.

Design

Architecture document, UML models, DB schema, interface specs.

Source and build

Source code, build scripts, lockfiles, migration scripts, config files.

Test

Test plan, test cases, test data, automation scripts, coverage reports.

Documentation

User manual, installation guide, API docs, release notes.

Environment

Dockerfiles, IaC templates, CI config, compiler and library versions.

Rule of thumb

If losing it, or losing track of which version is which, would hurt the project, it is an SCI. Put another way: an artefact is an SCI if a later version of the product would be wrong or unreproducible without it.

Real life

Google keeps about 2 billion lines of code for almost all products in a single versioned monorepo, so every SCI in the company shares one identification scheme. Tools: Git + Git LFS, JFrog Artifactory / Sonatype Nexus, Jira and Confluence, DOORS.

03Baselines: the control point

Exam text (after IEEE Std 610.12)

A baseline is a specification or product that has been formally reviewed and agreed upon, that thereafter serves as the basis for further development, and that may be changed only through formal change control procedures.

Before a baseline, change is cheap and informal. After a baseline, every change must be requested, evaluated and approved.

BaselineEstablished whenContains
FunctionalSRS reviewed and signed offRequirements SCIs
Allocated / DesignDesign review passedArchitecture, UML, schema
DevelopmentalCode complete, unit-testedSource, build scripts
ProductSystem test passed, releasedExecutable, docs, test set
OperationalDeployed to productionRelease image + config
Memory aid

F-A-D-P-O: "Five Angry Ducks Paddle Over". Functional, Allocated, Developmental, Product, Operational.

Tools: Git tags and annotated release tags, release/* branches, Jira "Fix Version", immutable artefact repositories, signed release manifests. IEC 62304 and DO-178C make baselining auditable evidence: a regulator must be able to rebuild the exact version that was shipped.

04The SCM repository

Exam text

The SCM repository is the set of mechanisms and data structures (typically a database) that acts as the centre for accumulation and storage of software engineering information, allowing a team to manage change effectively.

Data integrity

Validates entries; a change to one SCI cannot silently break dependants.

Information sharing

One authoritative copy for every team member and every tool.

Tool integration

Editors, build, test and issue tools operate on the same objects.

Data integration

Relationships and dependencies between SCIs are stored, not guessed.

Methodology enforcement

Workflow rules (review before merge) are applied by the repository.

Document standardisation

Templates and required metadata are built into the object model.

It stores: configuration objects, versions and variants, dependency links, change history, review and audit records.

Memory aid: six repository functions

I-S-T-D-M-D: "Integrity, Sharing, Tools, Data, Methodology, Documents".

05The five SCM layers

LayerWhat it does
IdentificationEvery new SCI gets a unique name, type and owner. This layer always applies.
Version controlEach SCI is assigned to a specific version of the software; all changes are captured with who, what, when and why.
Change controlApplies only once a change is requested against a baselined SCI: evaluation, approval, implementation, verification.
Configuration auditingChecks that the change was made as specified and that all related SCIs were updated consistently.
Status reportingThe record of every SCI (name, creation date, version, change history) published to stakeholders.
Exam trap

Change control applies only to baselined SCIs. Identification always applies. Automotive SPICE and CMMI level-3 appraisals check all five layers separately: a team with version control but no audit layer fails the configuration-management process area.

06Version control, branching and semantic versioning

Exam text

Version control combines tools and procedures to manage different versions of configuration objects. It records every change to every file together with the reason for the change and the identity of who made it and when.

Version database

Stores all versions and variants.

Version management

Constructs a specific version on demand.

Make facility

Builds the release from selected versions.

Issue tracking

Links each change back to a request or defect.

Exam text: semantic versioning MAJOR.MINOR.PATCH

MAJOR: incompatible / breaking change (2.3.1 → 3.0.0). MINOR: new capability, backward compatible (2.3.1 → 2.4.0). PATCH: backward-compatible bug fix only (2.3.0 → 2.3.1).

Exam trap

When MINOR goes up, PATCH resets to 0. When MAJOR goes up, both MINOR and PATCH reset to 0. And: a version replaces its predecessor in time; a variant coexists with it (a hospital build and a clinic build of the same release).

Google and Meta run trunk-based development at scale, hiding unfinished work behind feature flags rather than long-lived branches. Tools: Git branch/merge/rebase, pull and merge requests with CODEOWNERS, Gerrit, semantic-release, Conventional Commits, Changesets.

07The change control process

StageSteps
1 Evaluate and decideNeed for change recognised → change request submitted → developer evaluates → change report → Change Control Authority (CCA / CCB) decides. Approved → queued for action. Denied → user informed, closed.
2 ImplementAssign engineers to the configuration objects → "check out" the SCIs (lock / branch) → make the change (design, code, tests, docs) → formal technical review → "check in" the SCIs.
3 VerifyEstablish a baseline for testing → perform SQA and regression testing → software configuration audit (SCA) → review the change against all configuration items.
4 ReleasePromote change for inclusion in the next release → rebuild the appropriate version → include the change in the new version → distribute / deploy the new version.
Request→Change report→CCB decides→Check out→Change + review→Check in→Test + audit→Rebuild + release
Memory aid: the four stages

E-I-V-R: "Every Idea Verified, Released".

Key point

Check-out / check-in are the access-control and synchronisation mechanisms. An SCI that is checked out is locked or branched, and cannot be checked in until review passes.

Real life

ITIL change management splits requests into standard, normal and emergency paths. Emergency fixes bypass the CAB meeting but are audited retrospectively within 24 hours. Tools: Jira Service Management, ServiceNow, Azure DevOps Boards, merge requests with required reviewers, Engineering Change Orders (ECO).

08Configuration audit and status reporting

Review vs audit

A formal technical review checks whether the modified SCI is technically correct. The configuration audit is complementary: it checks whether the change was made the way the process requires.

Exam text: the five audit questions
  1. Was the change specified in the Engineering Change Order actually made, and were any extra, unrequested modifications sneaked in?
  2. Was a formal technical review held to assess technical correctness?
  3. Was the software process and the SCM procedure followed?
  4. Has the change been highlighted in the SCI, with date, author and reason recorded?
  5. Were all related SCIs (design, tests, user manual) updated consistently?
Memory aid

Scope, Review, Process, Record, Related: "Some Reviewers Prefer Reading Receipts".

Audits may be manual reviews, or fully automated checks inside the CI pipeline.

Configuration status reporting (CSR)

An SCM task that answers four questions for every change, and publishes the answers so that nobody works from a stale assumption:

What happened?

Which SCI changed, and from which version to which.

Who did it?

Author, reviewer and approving authority.

When did it happen?

Request, approval, implementation and release dates.

What else is affected?

Dependent SCIs, tests and documents requiring update.

Useful CSR metrics: change request approval rate, mean change cycle time, configuration stability, change backlog, unapproved-change count.

Exam text: formulas

Approval rate = approved ÷ decided × 100 (decided = approved + rejected)
Mean cycle time = Σ cycle times ÷ n
Median cycle time = middle value of the sorted list
Configuration stability = (total − changed) ÷ total × 100

Calculator: CSR metricsMediTrack Q4
Real life

US Executive Order 14028 requires suppliers to federal agencies to ship a Software Bill of Materials (SBOM): effectively a machine-readable configuration audit of every dependency. Tools: git log / blame / bisect, SPDX and CycloneDX, Jira dashboards, Grafana, OPA and GitHub branch protection.

09SCM in the CI/CD pipeline, GitOps and supply chain

Modern SCM is executable: the pipeline itself enforces identification, version control and auditing on every commit.

Commit
signed, on a feature branch→CI build
reproducible, pinned deps→Automated tests
unit, integration, regression, security→Artefact
immutable, versioned image→Release and deploy
tagged, auto release notes

Reproducible builds

Same source + same pinned dependencies + same toolchain ⇒ byte-identical artefact. Lockfiles (package-lock.json, go.sum, poetry.lock) are themselves SCIs.

Immutable artefacts

A published artefact is never overwritten. A fix produces a new version number, never a silent replacement of v2.3.0.

Traceability

Commit → change request → test run → artefact → deployment must form an unbroken chain, so any production binary can be traced to its source.

Release train: commit → build → test → stage → production, with the version number carried unchanged through every stage. If it is rebuilt, it is a different version. Amazon reached a deployment roughly every 11.7 seconds by making the pipeline, not a person, the change-control gate.

Where the discipline is heading

GitOps

The Git repository is the single declarative source of truth for infrastructure as well as code. A controller reconciles the running system with the committed state, so drift is corrected automatically. Every infra change is a reviewed PR; rollback = revert a commit.

ArgoCD, Flux

Infrastructure as Code

Servers, networks, clusters and pipeline definitions become versioned SCIs. Environments become reproducible from the repository.

Terraform, Pulumi, CloudFormation, Ansible, Kubernetes + Helm

Supply-chain integrity

A configuration includes hundreds of third-party dependencies. Managing them, and proving where each came from, is now core SCM.

SBOM (SPDX, CycloneDX), Dependabot / Renovate, Sigstore, SLSA

The slide marks this as an extension of the source chapter. After the SolarWinds build-system compromise, provenance and reproducible builds moved from good practice to a procurement requirement.

10Exercise: the MediTrack patient monitoring system

Scenario

MediTrack is a hospital patient-monitoring web application classified as IEC 62304 Class B. A six-developer team maintains it. The production release is v2.3.0, baselined as B3 on 01-Sep. The repository has main, release/2.3 and short-lived feature branches. Three change requests are open: CR-104 (critical defect: the vitals alarm threshold fires one unit late), CR-111 (add SMS alerting for on-call nurses) and CR-118 (remove the deprecated REST v1 API).

6 marks

Q4: CSR metrics

In September the CCB logged 24 change requests: 15 approved, 6 rejected, 3 pending. Cycle times of the 15 approved requests (days): 2, 3, 5, 1, 4, 6, 2, 3, 8, 2, 4, 5, 3, 2, 10. 180 baselined SCIs, 27 modified. Compute approval rate, mean and median cycle time, and configuration stability. (Use the calculator in section 08 to check.)

Solution

Approval rate = 15 ÷ (15 + 6) × 100 = 71.4%. Against all 24 logged requests it is 62.5%; 3 are still pending a decision.

Mean cycle time = 60 ÷ 15 = 4.0 days. (Cycle time = date approved → date change released.)

Median: sorted 1, 2, 2, 2, 2, 3, 3, 3, 4, 4, 5, 5, 6, 8, 10 → 8th value = 3.0 days. Median < mean: two long requests (8 and 10 days) skew the average upward. Report both.

Configuration stability = (180 − 27) ÷ 180 × 100 = 85.0%. 15% of the baseline churned in one month: high for a Class B medical product nearing release.

Interpretation: two thirds of requests clear in ≤ 4 days, so the process is not the bottleneck. The 8 and 10-day tail waited for the weekly CCB. 85% stability plus 3 pending requests means the release is not ready to freeze. Action: move low-risk requests to a pre-approved standard-change list.

11More exam practice with model answers

10 marks

Case: Nagad app release

Nagad's app is at v5.8.2. Pending: (1) a crash when the balance is exactly zero; (2) a new "pay utility bill by QR" feature; (3) the old login API that takes a PIN in the URL is removed for security. A developer pushed a "quick fix" to the release branch at 2 am without a ticket. (a) Give the version after each change in release order. [3] (b) Which audit questions does the 2 am push fail, and what should happen now? [3] (c) Name the five SCM layers and say which layer would have stopped the 2 am push. [4]

Model answer

(a) 5.8.2 → 5.8.3 (crash fix, PATCH) → 5.9.0 (new compatible feature, MINOR) → 6.0.0 (breaking removal, MAJOR). The crash fix ships first from a hotfix branch.

(b) It fails Q2 (no formal technical review) and Q3 (the SCM procedure was not followed: no change request, no CCB). Q4 also fails if no reason was recorded. Now: raise a retrospective change request, review the change, run regression tests, record it in the ECO, or revert it.

(c) Identification, version control, change control, configuration auditing, status reporting. Change control should have stopped it: the release branch holds baselined SCIs, so a change needs a request and approval. In practice, branch protection with required reviewers enforces this; the audit layer detects it afterwards.

5 marks

Practice: baselines

Define a baseline (IEEE). Name the five typical baselines and say when each is established. Why is the baselined version never edited in place?

Model answer

A baseline is a specification or product that has been formally reviewed and agreed upon, that thereafter serves as the basis for further development, and that may be changed only through formal change control procedures. Functional (SRS signed off), Allocated / design (design review passed), Developmental (code complete, unit-tested), Product (system test passed, released), Operational (deployed to production). It is never edited in place because a regulator or team must be able to rebuild the exact version that shipped; a change produces a new, approved version (v1.0 → v1.1) through check-out and check-in.
