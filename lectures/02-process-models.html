Software development process models

From plan-driven models to agile methods. Every model arranges the same basic activities in a different order. You must explain each one, choose the right one for a project, and do the velocity, burndown, MoSCoW and FDD calculations.

01Software process and process models

Software process

A structured set of activities required to develop a software system.

Software process model

An abstract representation of a process. It describes the process from a particular perspective: what is done, in what order, by whom, and producing what.

Five generic framework activities

Communication
gather requirements→Planning
estimate, schedule, risk→Modeling
analysis and design→Construction
code and test→Deployment
deliver, support, feedback
Memory aid

C-P-M-C-D: "Can Pressman Make Coffee Daily?"

Umbrella activities span every phase: project tracking and control, risk management, quality assurance, technical reviews, configuration management, documentation.

Key point

Models differ only in how they order the framework activities: linear, iterative, incremental, evolutionary or parallel.

A map of process models

FamilyIdeaModels

The models sit on a spectrum. Predictive (plan-driven): heavy up-front planning, stable requirements. Adaptive (agile): light planning, embraced change, frequent feedback.

02Waterfall (linear sequential) model

Exam text

A linear, sequential model: the project is partitioned into distinct stages that flow downward like a waterfall, each completed before the next begins.

Use when

Requirements are well understood and stable. Technology is familiar and the project is short. A fixed-price contract needs fixed scope.

Problems

Inflexible partitioning, no backtracking. Hard to respond to changing requirements. Working software appears late, and defects found late cost most (Lecture 1).

Tools: Gantt charts (MS Project), stage-gate reviews, requirements baselines (IBM DOORS), formal SRS/SDD templates (IEEE 830/1016). Industry: fixed-bid government and public-sector contracts, legacy maintenance with stable scope, hardware-coupled projects.

03V-Model (verification and validation)

Exam text

An extension of the waterfall in which every development phase has a directly associated testing phase, executed sequentially in a V-shape. Highly disciplined: the next phase starts only after the previous one ends.

Strengths

Tests planned early. Full traceability. Defects caught near their source.

Limitations

Still rigid to change. No early working prototype. Costly for evolving needs.

Tools: requirement-test traceability matrices; IBM DOORS, Siemens Polarion, Jama Connect; OpenText ALM. Industry: automotive (ISO 26262), medical devices (IEC 62304), avionics (DO-178C), German public sector (V-Modell XT).

Exam trap

Match each pair correctly: requirements ↔ acceptance, system design ↔ system testing, architecture ↔ integration, module design ↔ unit. Coding is the point of the V.

04Prototyping and evolutionary development

Listen to customer→Build / revise mock-up→Customer test-drives mock-up↻ iterate until requirements are clear

Prototyping model

Used when requirements are not clear. The prototype is a mechanism for discovering them. It iterates as the prototype is tuned to satisfy the customer.

Risk: customers mistake a prototype for the finished product.

Exploratory development

Work with customers to evolve the final system from an outline spec. Start with WELL-understood requirements.

Throw-away prototyping

Goal: understand the requirements, then discard the prototype. Start with POORLY understood requirements.

Exam trap

Exploratory starts with well-understood requirements and keeps the result. Throw-away starts with poorly understood requirements and discards the prototype. Students swap these.

Requirements always evolve, so reworking earlier stages is a normal part of large projects.

Tools: Figma, Balsamiq, Axure RP, paper sketches and wireframes, clickable mock-ups, Wizard-of-Oz tests, A/B tests. Industry: UX of mobile and web apps, start-up MVPs, research systems.

05Incremental development

Key characteristics

Delivered as a series of increments, each adding part of the functionality. Highest-priority requirements go in the earliest increments. An increment's requirements are frozen once it starts; later ones can still evolve.

Advantages

Customer value delivered early. Early increments act as prototypes to elicit later requirements. Lower risk of total project failure. Highest-priority services receive the most testing.

Real life

ERP roll-outs module by module (finance first, then HR and payroll). A university system that launches course registration first and adds result publishing and fee payment later.

06Spiral model (Boehm, 1986): risk-driven iteration

Exam text

An evolutionary model that combines the iterative nature of prototyping with the controlled, systematic steps of the waterfall. Each loop of the spiral is driven by explicit risk analysis before committing more resources.

  • Risk exposure = probability × impact. Resolve the highest first.
  • Early loops produce a concept or prototype; later loops produce the full system.
  • Incremental development can follow a spiral pattern.
  • Limitation: needs risk-assessment expertise; costly for small projects.

Tools: risk registers, simulations, benchmarking, prototypes. Industry: large, high-risk defence, aerospace and new-technology programmes.

07Rapid application development (RAD)

Requirements planning
needs, scope, constraints agreed→User design
users and analysts build models and prototypes⇆Construction
components developed→Cutover
testing, changeover, training

User design and construction iterate. Components are built in parallel as mini-projects (Team A → module 1, Team B → module 2, Team C → module 3), then integrated in about 60 to 120 days.

  • A type of incremental model. Developments are timeboxed, delivered and assembled into a working prototype.
  • Requirements are frozen within each increment.
  • The customer sees and uses something quickly, so feedback is fast.
  • Target: a fully functional system in 90 days, give or take 30.
  • Needs: a modular system, skilled developers, committed users.

Tools: JAD (joint application design) workshops, CASE and low-code tools: OutSystems, Mendix, Power Apps, Oracle APEX. Industry: internal business apps, dashboards, workflow and portal systems.

08Component-based development (CBD)

Build systems by integrating pre-built, reusable components (OO classes, libraries, services, COTS) instead of writing everything from scratch.

Identify candidate components→Look up components in library→Available?yes →Extract components/ no →Build components → put in library→Construct nth iteration↻ next iteration

Benefits

Shorter development time, lower cost. Proven, tested building blocks.

Risks

Version and dependency conflicts, licensing. Integration effort can exceed "build" (the Lecture 1 myth).

Tools: npm, Maven, NuGet, PyPI, JFrog Artifactory, Sonatype Nexus; Docker Hub. Industry: nearly all modern software: React component libraries, Spring Boot starters, microservices, SAP and Salesforce add-ons.

10Risk profile: why iterate?

Waterfall

Risk stays high until integration and testing. Integration surprises appear late, so there is big scrap and rework.

Iterative

Products are visible at early stages. Each iteration integrates and tests, so risks are retired early. Low probability of rework in the delivered product.

Link to Lecture 1: the cost of fixing a defect grows steeply the later it is found. Iteration finds defects earlier.

12Agile software development

Exam text: agility and the agile model

Agility: the ability to create and respond to change in order to profit in a turbulent business environment.

Agile model: a subset of iterative and evolutionary methods: lightweight, people-based rather than plan-based, delivering working software in short iterations of 1 to 4 weeks.

Why companies need agility

Innovate with better and faster operations. Respond quickly to competitors and new technology. Respond to changing customer requirements.

Agile proponents believe current processes are

Too heavyweight (much work unrelated to the product). Too rigid for incomplete or changing requirements. Lacking short cycles and active customer involvement.

Barry Boehm

Plan-driven methods work best when developers can determine the requirements in advance and when the requirements remain relatively stable (change rates of about 1% per month).

Anatomy of an agile iteration

Req.→Design→Build→Test→Iteration release (integrated and tested)↻ feedback + new information

3 to 6 months

Iteration length in past iterative methods.

1 to 4 weeks

Agile iteration length: intentionally never over 30 days.

Each iteration is a self-contained mini-project. It spans requirements, design, implementation and test. Its output grows into an evolving subset of the final system. Research shows shorter iterations give lower complexity and risk, better feedback, and higher productivity and success rates.

Timebox and scope: fix the time, flex the scope

Plan-driven thinking

Scope is fixed, so the schedule stretches. Result: late delivery, budget overrun (the software crisis).

Agile timebox

Iteration length is fixed, so scope is chosen to fit.

855
2-week timebox = 20 pts capacity. The 13 and 3 point stories go to the next iteration.
Exam text: the timebox rules
  • The pre-determined iteration length serves as a timebox for the team.
  • The scope (set of tasks or stories) is chosen to fill the iteration length.
  • Rather than increasing the iteration length to fit the chosen scope, the scope is reduced to fit the iteration length.

16Timeboxing and velocity planning

Velocity is the number of story points a team completes per iteration. Use the average of recent iterations to plan. Then fill each timebox with stories in priority order, and stop when the next story does not fit.

Planner: velocity and iteration scopeExercises 2 and 3
Exam trap

"Strictly in priority order" means you do not skip ahead to a smaller story that would fit. In Exercise 2, iteration 1 stops at 18 points even though a 3-point story exists later. A story never splits across iterations.

17Extreme Programming (XP)

Exam text

A lightweight agile method evolved from the problems of long development cycles (Beck, 1999). It assembles practices found effective in earlier decades and pushes them to the extreme; practices are tailored to each project.

Origin: Kent Beck, Chrysler C3 payroll project (1996); book "Extreme Programming Explained" (1999).

The five XP values

Communication

Oral culture; practices force interaction. Most problems trace back to someone not talking.

Simplicity

Design the simplest product that meets today's needs. No speculative features.

Feedback

From customers every iteration and release. It drives the next iteration.

Courage

For example, resist pressure to make unrealistic commitments.

Respect

Team members care about each other and the project.

Memory aid

C-S-F-C-R: "Cats Sleep For Cozy Rest".

XP lifecycle: five phases plus death

PhaseWhat happens
1 ExplorationCustomers write story cards for release 1. The team learns tools, technology and practices. A few weeks to a few months.
2 PlanningUser stories written and prioritized. Programmers estimate effort. Release planning creates the schedule.
3 Iterations to releaseSeveral iterations of 1 to 4 weeks. The 1st iteration builds the whole-system architecture. The customer picks stories per iteration.
4 ProductionizingExtra testing and performance checks. Decide on late changes. Iterations may shrink (3 → 1 week). Postponed ideas are documented.
5 MaintenanceKeep production running while building new iterations. Customer support effort. Velocity may slow; the team may change.
6 DeathNo more stories; needs met (performance, reliability). Final documentation written. Or: the system fails or is too costly.

Feedback loop: results of each iteration feed the next planning game. Functional (acceptance) tests run at the end of every iteration. The first release is typically productionized within 2 to 3 months.

Memory aid

E-P-I-P-M-D: "Every Programmer Iterates, Polishes, Maintains, Dies".

XP roles

Customer

Writes stories and functional tests; sets priorities; decides when a requirement is satisfied.

Programmer

Writes tests and code; keeps the code as simple and definite as possible.

Tester

Helps the customer write functional tests; runs them regularly; broadcasts results; maintains tools.

Tracker

Traces estimates vs actuals to improve estimation; checks whether the iteration goal is reachable.

Coach

Responsible for the process as a whole; guides the team in following XP.

Consultant

External member with specific technical knowledge the team needs.

Manager (Big Boss)

Makes the decisions; communicates with the team about the current situation.

Key point

Customer + Programmer are the core pair: one decides WHAT and WHEN, the other estimates HOW LONG and HOW. One person may hold several roles (coach + tracker), but the customer must never be replaced by a programmer guessing requirements.

XP practices

Planning game

Programmers estimate stories; the customer decides scope and release timing.

Small releases

Productionize a simple system fast; new versions at least monthly.

On-site customer

Customer present and available full-time to the team.

Metaphor

A shared story of how the system works guides development.

Simple design

Simplest solution implementable at the moment.

Refactoring

Remove duplication, simplify, add flexibility. Behaviour unchanged.

Testing (TDD)

Unit tests written first and run continuously; customer acceptance tests.

Pair programming

Two people, one computer: driver + navigator.

Continuous integration

New code integrated as soon as it is ready; all tests pass.

Collective ownership

Anyone can change any part of the code at any time.

Coding standards

Shared rules; code that communicates clearly.

40-hour week

Sustainable pace: a maximum 40-hour working week.

Open workspace

Large room with small cubicles; team co-located.

Just rules

Team-owned rules; changed by agreement after assessing impact.

Why it works: practices reinforce each other. Tests make refactoring safe. Pairing spreads ownership.

Pair programming, TDD and continuous integration

Pair programming

Driver: keyboard; tactical; writes code. Navigator: observes; spots defects; thinks strategically. Switch roles periodically.

Benefits: fewer defects, instant review, knowledge sharing, collective ownership. Cost: two people per task, offset by less rework. Remote: shared editors (VS Code Live Share, Tuple).

TDD cycle

CI loop, many times a day: commit → build → run all tests → integrate.

18Scrum

Exam text

An iterative, incremental framework in which a self-organizing team delivers the product in short, fixed-length Sprints, adapting to change through regular inspection of the product and the process.

Origin: Takeuchi and Nonaka (1986), adaptive, quick, self-organizing product development from Japan. The name is a rugby term: getting an out-of-play ball back into the game through teamwork. Formalized by Schwaber and Sutherland (1995). Empirical pillars: transparency, inspection, adaptation.

Three phases

Pre-gameDevelopment (game)Post-game
Planning: define the system; create the Product Backlog of all known requirements; prioritize and estimate; define team, tools, resources, risks, training, approval.
Architecture: high-level design from current backlog items; for enhancements, identify changes and problems; a design-review meeting decides.		Treated as a "black box": the unpredictable is expected. Functionality developed or enhanced in Sprints (1 week to 1 month) to give new increments. Each Sprint: requirements, analysis, design, evolution, delivery.Entered when all agree the requirements are complete and no more items or issues can be found or invented. Release preparation: integration, system testing, documentation.

The Product Backlog is updated continuously (new items, better estimates, new priorities) throughout all three phases.

The Scrum process flow

Roles

Scrum Master

Ensures the project follows Scrum practices, values and rules and progresses as planned. Interacts with team, customer and management. Removes impediments. Runs the Daily Scrum.

Product Owner

Officially responsible for the project. Manages, controls and makes visible the Product Backlog. Makes final backlog decisions. Selected by the Scrum Master, customer and management.

Scrum Team

Self-organizing; has authority to decide actions to reach each Sprint goal. Estimates effort, creates the Sprint Backlog, reviews the Product Backlog, flags impediments.

Customer

Participates in tasks related to Product Backlog items for the system being built or enhanced.

Management

Final decision-making; sets agreements, standards and conventions; helps set goals and requirements.

Modern note

The Scrum Guide (2020) defines three accountabilities: Product Owner, Scrum Master and Developers. Customers and managers are stakeholders.

Key point

PO decides WHAT (priorities). The team decides HOW (and how much per Sprint). The Scrum Master protects the PROCESS.

Ideal burn rate = committed points ÷ Sprint days
Actual rate = points completed ÷ days elapsed
Velocity = points completed per Sprint

Exam trap: what Scrum says when you are behind

Raise it in the Daily Scrum. The Scrum Master removes impediments. The PO and team renegotiate scope (drop lowest-priority items). The Sprint is NOT extended. In the retrospective, plan nearer the real velocity next Sprint.

20Dynamic Systems Development Method (DSDM)

Exam text

A public-domain Rapid Application Development framework built from the experience of many vendor and user organisations (DSDM Consortium, UK, 1994); the UK's de-facto RAD standard. It fixes time and resources and flexes requirements, addressing current and imminent business needs rather than every perceived possibility.

Today: DSDM / AgilePM, Agile Business Consortium. Motto: deliver what the business needs, when it needs it.

Memory aid

F-B-F-D-I: "Five Busy Friends Drink Iced-tea". Feasibility, Business, Functional model, Design and build, Implementation.

Fixed time, flexible functionality

  • Fundamental assumption: nothing is built perfectly the first time.
  • In DSDM any step can be revisited, so each step need only be complete enough to move on.
  • Traditional practice spends much time getting from the 80% solution to 100%, assuming no step is revisited. The result is late, over budget, or misses business needs.
Exam text: the 80:20 rule

A usable, useful 80% of the system can be produced in 20% of the total time.

Consequence: the deadline is never moved. Lower-priority requirements are deferred (MoSCoW).

Techniques: timeboxing, prototyping, workshops

Timeboxing

Nested timeboxes inside a project timebox give a series of fixed deadlines (ideally 2 to 4 weeks). Focus on WHEN a business objective is met, not on tasks. The easiest 80% is produced in each timebox; the remaining 20% may be carried forward. Without it, prototyping teams lose focus.

Prototyping

Workshops set high-level requirements; prototypes let users check the DETAIL is right. Demonstrations broaden users' awareness of possibilities and trigger feedback. Speeds development and raises confidence the right solution is delivered.

Facilitated workshops

Goal: clear outcomes reached by consensus. Participants: sponsor, development team, scribes, observers, prototypers, facilitator. The facilitator helps the group understand common objectives. Types: business, usability, performance and capacity, capability/technique.

Advantages: speed, ownership, productivity, consensus, better decisions, synergy.

22Feature-Driven Development (FDD)

Exam text

An agile, short-iteration process that delivers the system feature by feature. It combines key advantages of other agile approaches with industry best practices (domain modelling, inspections, class ownership) and was designed to scale to much larger projects and teams.

History: Jeff De Luca (project manager and original creator, with Peter Coad's modelling), 1997, a Singapore bank loan-automation project with a 50-member team. First published in "Java Modeling in Color with UML" (1999). Motto: model first, then deliver client-valued features every two weeks or less.

What is a feature?

Exam text

A small function expressed in client-valued terms that presents a customer requirement to be developed in a short iteration. Maximum 2 weeks; most take 1 to 5 days. Anything larger is split into smaller features.

Naming template

<action> the <result> <by | for | of | to> a(n) <object>

Calculate the total of a sale. Validate the password of a user. Authorize the sales transaction of a customer.

Three-level hierarchy: subject area (Sales Management) → business activity (Making a sale) → feature (Calculate the total of a sale; Print the receipt of a sale). Features are the unit of planning, design, build and progress reporting.

The five FDD processes

ProcessScopeActivities
1 Develop an overall modelProject-wide, up front: just enough design to build onForm modelling team (domain experts + chief architect); domain walk-through; build high-level object model; record notes
2 Build a features listDecompose domain into subject areas → business activities → features; each feature ≤ 2 weeks
3 Plan by featureInitial schedule at feature level; prioritize by business value, dependencies, difficulty, risk; assign feature sets to chief programmers and classes to owners
4 Design by featurePer feature, iterative, ≤ 2 weeksChief programmer forms a feature team (3 to 5); detailed design (sequence diagrams); design inspection; update model
5 Build by featureImplement designed feature; unit and feature-level tests; mandated code inspection; promote to the regular build
Memory aid

Model, List, Plan, Design, Build: "My Lovely Parrot Dances Badly".

Roles, class ownership and feature teams

Primary roles

Project Manager; Chief Architect (overall design); Chief Programmers (lead feature teams); Class Owners (own and change their classes); Domain Experts (business knowledge).

Supporting roles

Language Guru (shared vocabulary); Toolsmith (builds tools); Tester; Technical Writer (documentation).

Class ownership (FDD)Collective ownership (XP)
Who changes a class?Its assigned ownerAny developer, any time
StrengthClear responsibility for integrity; an expert per class; fast changesNo bottlenecks; shared knowledge

Feature teams: the chief programmer picks members by the classes the feature touches (3 to 5 people). Teams work concurrently and disband when the feature is done. A developer can be on several teams at once. Class ownership + dynamic feature teams = accountability AND flexibility, the key to scaling FDD.

Inspections and progress reporting

Design 40%Code 45%C-insp 10

Milestone weights: walk-through 1, design 40, design inspection 3, code 45, code inspection 10, promote to build 1. Sum = 100%.

Exam text: progress formula

Feature % = sum of weights of completed milestones. Feature set % = average of its features' %. Example: coded and inspected, not promoted = 1 + 40 + 3 + 45 + 10 = 99%.

Why mandated code inspections? They find more, and different, bugs than any other form of testing, and they are a great learning experience. Reporting is accurate, meaningful and timely for all stakeholders (for example colour-coded "parking-lot" charts).

5 marks

Practice: choose and justify

Bangladesh Bank wants a new real-time gross settlement module. Rules are fixed by regulation, every requirement must be traced to a test, and audits are strict. Which model and why? Why not Scrum?

Model answer

V-Model. Requirements are fixed and regulated. Each development phase has a paired test phase (requirements ↔ acceptance, system design ↔ system test, architecture ↔ integration, module design ↔ unit), which gives full traceability for audits. Defects are caught near their source. Scrum is less suitable: agile is unsuited to safety-critical work with heavy certification documentation, and its strength (welcoming change) is not needed when requirements are fixed by law.
